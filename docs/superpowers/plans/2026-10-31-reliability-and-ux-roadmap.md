# Cloakwire reliability and UX Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Реализовать все согласованные улучшения подключения, профилей, диагностики, маршрутизации и интерфейса на Windows, macOS и Android, сохранив работающие сценарии 1.4.9.

**Architecture:** Поэтапно расширить существующих владельцев соединения: ProcessManager на desktop и VpnService на Android. Отдельно вести состояние процесса, здоровье выбранного профиля и здоровье активной сессии. UI показывает native данные; сетевые таймеры и восстановление остаются в native layer.

**Tech Stack:** Rust/Tauri 2, React/TypeScript, Kotlin/Android, существующие sing-box/libbox и Xray; Vitest/Cargo/JVM/Playwright и выделенные устройства.

**Spec:** [Архитектура и требования](../specs/2026-10-31-connection-reliability-and-ux-design.md)

**Дата:** 2026-10-31.
**База:** fadbaa6d6e833700a40f4815f2a6cb5fe957171b, версия 1.4.9.
**Статус:** утверждён пользователем; реализация начата в feat/connection-reliability-ux. D0: безопасный baseline готов; системные проверки требуют выделенных устройств.
**Исполнение:** предлагается последовательная реализация одним исполнителем с независимым ревью крупных этапов; это сохраняет единый контекст lifecycle и снижает конфликтующие изменения.

## Global Constraints

- Сохранять существующие поколения запуска и отмены; поздний результат старой операции не меняет новое подключение.
- Диагностическая проба не меняет системный прокси, маршруты, TUN, выбранный сервер или постоянный профиль.
- Проверять профиль тем ядром, которым он запускается. Не преобразовывать sing-box-профиль в Xray ради зелёного результата.
- Сохранять действующую проверку готового профиля до остановки рабочего подключения.
- Сетевой результат не подменяет состояние процесса; отказ тестового сайта не доказывает падение VPN.
- Не менять существующие DNS/GeoIP/provider rules, ограничения Xray desktop и политику защиты при обрыве.
- Данные подписки остаются под управлением native backend; WebView получает ссылки на записи и безопасные результаты.
- Все новые строки переводить на русский, английский и упрощённый китайский.
- Не добавлять телеметрию; не писать UUID, ключи, subscription URL, полный конфиг и сырые ошибки ядра в новый диагностический отчёт.
- Не обновлять ядра/библиотеки и не повышать минимальные версии ОС в рамках этой работы без доказанной необходимости.
- Тесты, меняющие сетевые настройки, запускать в выделенной VM/тестовом устройстве; на рабочем ПК — только проверки без системных изменений.

| 4. Видимый результат | B4, B5 | Статусы, действия ошибок, selected/connected, читаемость | Автотесты UI + визуальная и native WebView проверки |

Android D3 состоит из двух частей: сначала scoped process cleanup + техническое доказательство изоляции, затем продуктовый probe. Этап не считается завершённым при неподтверждённой возможности libbox. Если feasibility не проходит, архитектура адаптера пересматривается до продолжения; рабочий запуск VPN остаётся прежним.

## Что защищает работающие сценарии

- Сначала тест воспроизводит нежелательное изменение; затем минимальная реализация. Каждый task заканчивается проверками и отдельным коммитом.
- Проверка нового кандидата не прерывает действующее подключение. UI не объявляет кандидат активным до принятого native start.
- Для recovery используется активное ядро. Успешный временный процесс сам по себе не доказывает, что текущий VPN исправен.
- Новое автовосстановление изначально выключено для существующих установок. Включение — явная настройка; Stop всегда имеет приоритет.
- Текущие позиционные subscription index-N не переименовываются в «стабильные серверные IDs»: refresh меняет content revision; активный snapshot живёт отдельно.
- Откат профилей — текущий совместимый mirror и обработка правок старой версией, не восстановление устаревшего backup.
- Проверки live TUN/proxy/firewall выполняются в изолированной VM/устройстве, не на рабочей сети пользователя.
- Не запускать release build после каждого косметического изменения. Полные сборки нужны на контрольных точках, кэши повторно используются.

## Итог архитектурного ревью

Независимый ревьюер выявил семь существенных рисков; все включены в спецификацию и задачи:
1. Различить проверку профиля и действительно работающей сессии.
2. Исключить взаимное завершение Android Xray процессов и stale restart thread.
3. Описать Auto и смену фактического участника selector/urltest.
4. Сохранить позиционную семантику подписок с revision guards.
5. Обработать downgrade→edit→upgrade и одинаковые tag.
6. Зафиксировать реальную разницу защиты при обрыве Windows/macOS/Android без новых обещаний.
7. Доказать Android libbox/DNS/socket isolation, а не только отдельный process.

Повторное ревью: существенных неотвеченных вопросов или противоречий не осталось. Android isolation, active-route attribution и Android blackhole-preserving recovery остаются явными техническими воротами проверки; это не уже подтверждённые возможности.
