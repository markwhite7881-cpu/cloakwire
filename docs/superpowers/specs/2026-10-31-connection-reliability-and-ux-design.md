# Cloakwire: надёжность подключения и понятный интерфейс

Дата: 2026-10-31
Статус: проект для проверки; список улучшений согласован пользователем, детали реализации предложены агентом.
Базовый коммит: fadbaa6d6e833700a40f4815f2a6cb5fe957171b (исходники приложения 1.4.9).
Платформы: Windows x64, macOS arm64/x64, Android arm64-v8a.

## Цель и границы

Реализовать все десять предложенных улучшений: реальную проверку сервера; обновление ручного профиля при импорте; понятные ошибки после запуска; проверки настоящими ядрами перед выпуском; восстановление после сна/смены сети; подробные состояния подключения; явные режимы маршрутизации; информативные списки серверов; действия в карточке ошибки; читаемость и согласованность оформления.

Существующие импорт, подписки, GeoIP, DNS, маршрутизация, ядра и обновления должны сохранить поведение, кроме явно описанных новых действий пользователя. Номер следующего релиза выбирается при выпуске. Этот пакет документов не разрешает публикацию нового релиза или установку тестовых сборок поверх рабочей версии.

## Что установлено по коду

- Desktop useServerLatency измеряет TCP connect. Config preflight вызывает check ядра, но не проверяет доступ через сервер.
- Android LatencyTester уже выполняет запросы через временный Xray. Его нельзя считать универсальным тестером sing-box/Hysteria2/TUIC; фиксированные файл и ожидание запуска требуют изоляции.
- ProcessManager использует active_run_id, ready_check_epoch и переходный semaphore. Проверка готового профиля происходит до остановки активного соединения.
- Android имеет PendingProfileStarts, VpnEvents, монитор физической сети в CloakwirePlatform и ограниченный перезапуск умершего Xray. Новый координатор не должен конкурировать с ними.
- Manual profiles хранятся массивом Outbound в localStorage; выбор desktop привязан к tag. Импорт добавляет записи в начало списка.
- Android уже имеет all/include/exclude. Desktop использует vpn_processes/direct_processes/final_outbound. Пользовательские и провайдерские правила могут менять фактический маршрут.
- npm test:ui объявлен, но корневой конфиг Playwright и полноценная матрица UI-проверок не найдены. Наличие команды не является доказательством UI-проверки.
- В диагностике конкретного сервера новый набор параметров дал HTTP 204, а сохранённый — reality verification failed. Предварительные пробы без исключения активного VPN давали ложные таймауты. Реальные адреса и ключи пользователя не становятся fixtures.

## Подходы

1. Поэтапно добавить диагностику, стабильную идентичность профиля и представление поверх действующих владельцев VPN. Рекомендовано: узкие изменения, отдельные коммиты и проверяемые точки отката.
2. Переписать управление соединением в общую новую машину состояний. Не выбрано: затронет одновременно TUN, системный прокси, Android service и отмену проверок.
3. Только обновить оформление и сообщения. Не выбрано: не решает ложноположительную доступность сервера и устаревшие параметры.

Предлагается подход 1. Это инженерный выбор агента, а не утверждение о согласованных пользователем деталях. Нужна проверка этого документа перед изменением поведения приложения.

## Общие ограничения

- Сохранять существующие поколения запуска и отмены; поздний результат старой операции не меняет новое подключение.
- Диагностическая проба не меняет системный прокси, маршруты, TUN, выбранный сервер или постоянный профиль.
- Проверять профиль тем ядром, которым он запускается. Не преобразовывать sing-box-профиль в Xray ради зелёного результата.
- Сохранять действующую проверку готового профиля до остановки рабочего подключения.
- Сетевой результат не подменяет состояние процесса; отказ тестового сайта не доказывает падение VPN.
- Не менять существующие DNS/GeoIP/provider rules, ограничения Xray desktop и политику защиты при обрыве.
- Данные подписки остаются под управлением native backend; WebView получает ссылки на записи и безопасные результаты.
- Все новые строки переводить на русский, английский и упрощённый китайский.
- Не добавлять телеметрию; не писать UUID, ключи, subscription URL, полный конфиг и сырые ошибки ядра в новый диагностический отчёт.
- Не обновлять ядра/библиотеки и не повышать минимальные версии ОС в рамках этой работы без доказанной необходимости.
- Тесты, меняющие сетевые настройки, запускать в выделенной VM/тестовом устройстве; на рабочем ПК — только проверки без системных изменений.

## A. Идентичность и ревизии

Ввести ProfileRef: manual(id), subscription(subscription_id, link_key), ready(subscription_id, child_key), auto(snapshot_id). Auto представляет принятый snapshot набора профилей, а не произвольный отдельный сервер. Для существующих ручных записей создать случайный local id. Сохранить payload Outbound без UI-метаданных при отправке в генератор.

ManualProfileRecord = { id, revision, outbound }. Хранилище v2 записывается одним envelope {version:2, records}; legacy v1 читается при миграции и сохраняется для отката. Миграция идемпотентна; неудача записи не удаляет v1. Миграция выбора по старому tag допустима только при единственном совпадении. При неоднозначности показать необходимость выбора, не подключаться автоматически к другой записи.

Subscription keys index-N остаются позиционными, как в текущих тестах; это не постоянный идентификатор сервера. На refresh backend меняет revision содержимого позиции. Labels и действия используют пару reference+revision; активный snapshot сохраняется отдельно. Если запись с этой revision уже изменилась, действие просит повторно выбрать/проверить актуальную запись, а не применяется к новому серверу на старой позиции. Существующая семантика выбора подписки не мигрирует скрытно.

Runtime run_id идентифицирует реально запущенное соединение. Profile revision меняется при изменении соединительных параметров, не при переименовании. Для подписок backend вычисляет непрозрачную revision из нормализованного содержимого; секреты/их публичные хеши в UI не выводятся. Изменение данных подписки инвалидирует результаты проверки и не переключает активное соединение без существующего пользовательского действия.

Для контролируемого отката при каждой успешной v2-записи экспортировать совместимый v1 и хранить legacyMirrorFingerprint и legacyMirrorStatus. v2 остаётся единственным авторитетным envelope нового приложения; неудача mirror видна и запрещает объявлять откат подготовленным. Старый binary может изменить v1: при следующем upgrade несовпадение fingerprint означает конфликт, обе версии сохраняются, auto-connect приостанавливается до выбора/объединения пользователем. Совпавшие полные payload сохраняют id только при единственном совпадении. При одинаковых tag legacy lastServer не восстанавливается предположением. Нельзя восстановить старый backup поверх новых пользовательских изменений.

## B. Проверка сервера и состояния

Новый отдельный ConnectionHealth, без переопределения Status/VpnState:
- operation_id, scope: selected_profile | active_session, profile_ref, profile_revision, run_id (null для отдельной пробы), network_generation, effective_outbound_revision (null если неизвестен);
- stage: preparing | connecting | verifying | complete;
- outcome: unknown | checking | healthy | failed | unavailable | cancelled;
- issue: network_unavailable | endpoint_unreachable | timeout | reality_verification | tls_verification | dns | authentication | engine_unavailable | unsupported_probe | probe_target_unavailable | unknown;
- checked_at и latency_ms; raw log и конфиг отсутствуют.

RuntimeIssue отдельно содержит safe code, severity, run_id, occurrence count и разрешённые действия. authentication использовать только при явном подтверждении ядром. reality_verification не означает достоверно неверный UUID или ключ.

Политика проб:
- Триггеры: кнопка для выбранного профиля, один раз после успешного запуска, после пробуждения/смены сети для активной сессии.
- Не проверять целиком подписку по таймеру. Один полноценный probe на устройство; повтор идентичного запроса объединяется. Старый selection probe отменяется.
- Общий deadline 12 секунд, включая старт/запросы; отдельный cleanup budget 2 секунды. Свежесть 60 секунд; смена revision/run/network инвалидирует результат.
- Цели: HTTPS GET https://www.gstatic.com/generate_204 (строго 204), затем при сетевом сбое https://www.cloudflare.com/cdn-cgi/trace (200, ограничение ответа 4096 байт, структура trace). Не сохранять тело/IP. Не принимать redirect/страницу входа за успех. TLS-проверку не отключать.
- Успех любой проверенной цели подтверждает выбранный outbound, а не защиту всех приложений. Неуспех обеих целей без конкретной ошибки ядра = проверка доступа не удалась; не заявлять, что сломан сервер.
- TCP latency и подтверждённая задержка через профиль — разные показатели.
- После запуска VPN probe не блокирует кнопку Stop и не останавливает соединение при неуспехе.

Desktop adapter создаёт временную копию и отдельное ядро с частным loopback inbound, маршрутом теста к конкретному proxy outbound и полным сохранением необходимых detour/DNS/transport зависимостей. Системные inbounds отключены только в копии. Physical network binding использует актуальный разрешённый интерфейс, а не жёсткое Ethernet. Если нельзя доказать изоляцию или определить целевой outbound готового профиля, вернуть unavailable с причиной. Не выбирать first outbound наугад. Controller API можно использовать для активной сессии только если он подтверждает нужный конкретный outbound и поколение.

До конкурентных Android probes убрать глобальную очистку по имени libxray.so/pkill из обычного start/stop: lifecycle и diagnostics владеют отдельными process handles/leases. Recovery orphan cleanup подтверждает UID, путь config, token и start time, а не только PID/имя. Старый restart thread проверяет захваченное поколение сессии, а не один sessionActive.

Android adapter использует исходное ядро. Xray: развить существующий LatencyTester. Sing-box: отдельный непубличный Service в процессе :diagnostics, отдельные пути libbox/command sockets и запрет openTun. Настоящий VPN service не перезапускается. Технический эксперимент обязан доказать не только независимость процессов, но и изоляцию command sockets, DNS, всех TCP/UDP outbound sockets, cancellation и поведения lockdown. Проверить возможность этой изоляции в первом техническом эксперименте; неподдержанная возможность блокирует выпуск данного адаптера, не маскируется переходом на другое ядро. Физическая Network/защищённые сокеты выбираются через native слой; исключение собственного package не считать единственной гарантией обхода VPN при always-on/lockdown.

Нужны две разные проверки: selected_profile запускается отдельно и доказывает работоспособность профиля; active_session идёт через то же работающее ядро, чей run_id указан в результате. Active check использует конкретный outbound/controller или добавленный при подготовке runtime-копии аутентифицированный private loopback inbound с изолированным правилом для probe. Это правило не матчится на другие inbounds и не меняет маршруты обычных приложений. Оно проходит существующий preflight. Не подменять active check успешным вторым ядром.

В Auto и вложенных selector/urltest цепочках active check фиксирует выбранного участника до/после запроса; при смене участника сбрасывает результат и допускает одну повторную проверку. effective_outbound_revision идентифицирует эту цепочку, без раскрытия ключей. Если API ядра не подтверждает выбор, показывается состояние проверки active route с ограничением, а не отметка конкретного сервера. При выключенном VPN Auto не вызывает проверку всей подписки: предложить выбрать конкретный профиль.

Отдельный endpoint/profile probe проверяет outbound. Проверка того, что Windows/macOS TUN и Android include/exclude действительно направляют приложения правильно, выполняется отдельной системной матрицей, не выводится из HTTP 204.

## C. Импорт и обновление

Одинаковые host/port/protocol — только кандидаты для сравнения, не идентичность пользователя. Показать существующие ручные записи, изменённые категории полей без значений секретов и действия «Обновить выбранную запись», «Добавить отдельно», «Отмена». Полный дубль не добавлять без явного запроса. Несколько совпадений требуют выбора записи.

Обновление сохраняет id, пользовательское имя/tag, положение записи, выбор и глобальные правила. revision увеличивается; старый health сбрасывается. Внутри текущей сессии сохраняется snapshot: результат импорта не заменяет работающий конфиг, появляется обычное предложение переподключиться.

Записи подписок не заменяются ручным импортом. Для них доступно обновление своей подписки; ручная ссылка может стать отдельной записью. Refresh failure сохраняет последнее рабочее содержимое. Никакого исправления ключей предположением или обращения к серверной панели.

Нужно обнаруживать ошибку сохранения, а не закрывать импорт с ложным успехом. Проверка отложенного подтверждения сравнивает revision записи, чтобы старый диалог не перезаписал новую правку.

## D. Ошибки и UI

Новые статусы — производное представление:
- «Проверяем профиль» — native preflight;
- «Соединяемся» — исходный запуск;
- «VPN запущен · проверяем доступ» — процесс работает, probe идёт;
- «Подключено · сервер проверен» — свежий healthy для активной revision/run;
- «VPN запущен · доступ не подтверждён» — неопределённый сетевой результат;
- «Соединение нарушено» — подтверждённая runtime ошибка;
- «Отключено» после Stop, независимо от запоздалых событий.

Карточка не превращает единичный сбой одного destination в глобальное падение. Повторяющиеся ошибки объединяются по run+code. Произвольный stderr не выдаётся пользователю вместо безопасного сообщения. Действия: retry probe; reconnect по существующему пути; refresh принадлежащей записи subscription; открыть выбор сервера. Действия относятся к указанной записи и блокируют двойной запуск. Не показывать refresh для ручного профиля.

Selected и Connected видны отдельно. Активный snapshot остаётся обозначенным при смене выбранной записи, удалении её источника и неудачном переключении. Рядом с сервером: источник, TCP/проверенная задержка с разными подписями, время проверки, unknown/stale/healthy/failed/unavailable. Не показывать старый успех как текущий.

## E. Режимы маршрутизации

Desktop добавить явные all/include/exclude поверх существующих полей, Android использовать существующие tun_app_mode/tun_app_list. В обеих оболочках показывать дополнительные custom/provider правила и ограничения текущего ядра.

Существующие сложные настройки отображаются как custom, если невозможно однозначно вывести простой режим. Только открытие экрана ничего не преобразует. Переключение режима сохраняет custom rules, rule_sets, DNS и списки; если для режима нужно изменить конфликтующий список, показать конкретное изменение пользователю. Объекты для неактивного простого режима хранятся отдельно от исполняемых списков, чтобы при переключении не терять выбор и не выполнять скрытые исключения.

Include с пустым действующим списком не может молча превратиться в all. При custom/provider overrides формулировка «Только выбранные» относится к базовой политике, рядом явно указаны дополнительные правила. Xray desktop не обещает per-process capture, которого нет в текущей архитектуре.

## F. Восстановление

Добавить отдельную настройку «Восстанавливать соединение после сна и смены сети», по умолчанию выключена для существующих установок. Внутри нового варианта восстанавливается только сессия с явным user intent connected, только тот же принятый snapshot и то же ядро.

Native backend владеет coordinator; React показывает его состояние. Recovery использует active_session check; отдельный selected_profile success не доказывает, что существующий процесс исправен. Разрешение на restart: подтверждённое завершение процесса, либо две active_session ошибки в текущей network generation с подтверждённой физической сетью и успешным отдельным selected_profile probe. Один недоступный сайт/неопределённость доступа не дают разрешения на restart. На Android координировать с существующим engine-death restart, а не запускать два механизма. Не включать VPN при запуске приложения, если пользователь отключил его.

События: Windows power resume и смена доступного физического маршрута; macOS wake/path change; Android изменение non-VPN Network. Debounce 2 секунды, сначала health probe; если ядро само восстановилось — перезапуска нет. До 3 попыток с задержками 2/5/15 секунд, одна операция одновременно. Счётчик сбрасывается после 60 секунд подтверждённой стабильности, не после нового callback.

Stop, смена профиля, отмена разрешения VPN, закрытие соответствующего owner и новый connect отменяют старые задачи. Нет сети/страница авторизации — ожидание, не цикл перезапусков. Явная ошибка параметров — карточка, не ретраи. Сбой только проверочных сайтов без подтверждённой неисправности сессии не запускает reconnect.

Фактический baseline защиты различается: Windows firewall isolation сейчас отключена, desktop unexpected exit очищает системный proxy и снимает имеющееся состояние защиты; macOS module ведёт флаг, а strict_route принадлежит живому TUN; Android при настроенной защите может сохранять blackhole/TUN. Новая работа не обещает одинаковый fail-closed на платформах и не включает Windows firewall заново. Сохранять текущую policy TUN/proxy/kill switch и IPv6; не обходить блокировку прямым резервным маршрутом. Android recovery при активном blackhole не вызывает обычный full teardown до готовности замены. Для несовместимой политики восстановления вернуть понятное ограничение; не ослаблять защиту.

## G. Оформление

Сохранить узнаваемые темы и навигацию. Основные изменения: иерархия статуса/сервера/действия, единые размеры и отступы, читабельный вторичный текст, видимый keyboard focus, текстовые подписи вместе с цветом. Базовый информационный текст desktop 14px, mobile 14px; технические подписи минимум 12px. Touch targets mobile не менее 44x44 CSS px. Таблицы/карточки не обрезают длинные имена; RU/EN/zh-CN проверяются с реальной длиной строк.

Проверять system/light/dark/OLED и все 5 accent themes; reduced motion; keyboard; масштаб desktop 100/125/150/200%, минимальное окно 1040x680; mobile 360/390/430 CSS px и увеличенный текст. Браузерные снимки не заменяют проверку WebView2/WKWebView/Android WebView.

## H. Проверка и выпуск

## Внешние основания

Физические сети Android могут меняться вместе с объектом Network; использовать callbacks и корректную привязку сокетов: [Android network state](https://developer.android.com/develop/connectivity/network-ops/reading-network-state).
Исключение сокета из VPN поддерживается API [VpnService](https://developer.android.com/reference/android/net/VpnService).
Пробуждение Windows приходит как [PBT_APMRESUMEAUTOMATIC](https://learn.microsoft.com/en-us/windows/win32/power/pbt-apmresumeautomatic).
Проверки outbound в sing-box используют HTTP-цель, интервал и tolerance: [URLTest](https://sing-box.sagernet.org/configuration/outbound/urltest/).
