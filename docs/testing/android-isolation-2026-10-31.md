# Android: изоляция диагностики, 2026-10-31

Контрольная точка D3 поверх `1071871` в `feat/connection-reliability-ux`. Пользователь разрешил установить сборку и проверять подключённый телефон по ADB. В этом этапе проверяется безопасное сосуществование ядер; полноценная проверка пользовательских серверов и её интерфейс ещё не включаются.

## Изменения рабочего кода

- Xray-сессия и временный latency-тестер владеют отдельными process handles и уникальными конфигурационными файлами.
- Удалена очистка всех процессов по имени `libxray.so` и `pkill`. Закрытие владельца окончательно запрещает его последующий запуск, включая запоздалый restart thread.
- Очистка после гибели владельца рассматривает только записанные приватные leases. Проверяются UID, полная команда с точным config token, время запуска дочернего процесса и прекращение исходного процесса-владельца. Чужая запись, повторно использованный PID, живой или нечитаемый владелец не дают права завершить процесс.
- Старые процессы без доказанного владельца не завершаются по догадке. Неудавшееся завершение ребёнка не разрешает подмену его конфигурации новым запуском.
- Уведомления о смерти ядра и результат отложенного перезапуска привязаны к поколению принятой сессии. Остановка и публикация результата используют один порядок блокировки.

## Технический эксперимент

В `src/debug` добавлены непубличная bound service в процессе `:diagnostics` и shell-only Activity в отдельном `:diagnostic_driver`. Activity требует системное разрешение `DUMP`; диагностическая service не экспортирована. В release эти компоненты отсутствуют.

Эксперимент использует настоящий упакованный `libbox.aar`. Его синтетическая конфигурация не содержит пользовательских серверов или ключей. Выделены собственные base/working/temp paths, секрет command server и loopback inbound. Клиент управления сверяет уникальный outbound tag именно диагностического ядра.

Диагностика не создаёт TUN: попытка самого ядра открыть его получает отказ. Outbound file descriptors привязываются к конкретной физической Android Network; используется Network-specific DNS. Потеря доступной Network не запускает резервный маршрут. Применяются публичные [Android Network API](https://developer.android.com/reference/android/net/Network), а отдельный процесс обслуживается через [bound service/Binder](https://developer.android.com/develop/background-work/services/bound-services).

Обычное закрытие завершает собственный command client/server. Ограничение времени и отмена завершают только выделенный диагностический процесс; VPN-процесс не сигнализируется. Гибель Binder-клиента также закрывает диагностику.

Это feasibility harness, а не опубликованный API диагностики. Фиксированные внешние test endpoints используются только в явно запущенной проверке.

## Подтверждено на телефоне

CPH2747, Android 16, arm64. Перед обновлением сохранены предыдущий APK, localStorage и действительная полная конфигурация. Установка через `adb install -r` сохраняет данные.

На сборке с текущими изменениями:

- **12 PASS** в сценарии изоляции: отдельный процесс и command channel; физическая привязка сокетов; DNS; HTTPS 204 через диагностическое ядро; явный DNS-запрос через SOCKS5 UDP ASSOCIATE с новым outbound binding.
- Принятая VPN-сессия, её run ID и полная конфигурация не изменились при запуске и отмене диагностики, отказе создать TUN, гибели клиента и аварии диагностического процесса.
- Отдельное обычное Android-приложение получило HTTPS 204 через рабочий VPN во время диагностики и после отмены. Это проверка другого UID, не исключённого WebView Cloakwire.
- Повторный диагностический запуск после аварии прошёл.
- Регрессия карточки/отмены профилей: **9 PASS**, исходная конфигурация восстановлена.
- Сетевая матрица sing-box/Xray: **8 PASS**; оба режима включения/исключения приложения и отрицательные проверки кандидатов. После матрицы восстановлены полный принятый config, policy, engine, settings, profiles и selection.

Проверка изоляции выполнялась при активном sing-box. Сетевая матрица отдельно покрывает рабочий Xray; это не утверждение о всех сочетаниях одновременных диагностических операций с Xray.

- Новые проверки сначала не собирались без классов владения; конкурентная регрессия общей lifecycle-блокировки отдельно воспроизвела AssertionError до исправления и затем прошла.

Для воспроизведения нужен явно разрешённый телефон с работающим VPN и установленным вспомогательным APK:

```text
node scripts/android-isolation-check.mjs --adb <adb> --serial <device> --output <private-report.json>
```

Локальные копии, снимки и отчёты устройства находятся в игнорируемом каталоге `.superpowers`. В Git не записываются конфигурации пользователя, тела ответов или адреса внешнего выхода.

## Границы результата

- Изоляция проверена на одном Android 16 устройстве. Android 7+, lockdown/always-on, смена Wi-Fi/mobile, гибель всего процесса приложения и сон требуют отдельной матрицы.
- Lease-orphan policy проверена unit-тестами; реальная гибель владельца Xray с последующим восстановлением пока отдельно не воспроизводилась.
- Диагностическая конфигурация — синтетический direct proxy. Это доказывает сосуществование и socket/command ownership, но не реальную проверку конкретного VLESS/Reality/Hysteria2/TUIC профиля.
- Probe generation/snapshot, выбор конкретного сервера, разрешённая форма provider config, отмена при Stop/смене сети и продуктовый API остаются следующей частью D3.
- Принятое отключение при принудительном закрытии Android-задачи сохранено. Автовосстановление не включено; Windows/macOS runtime не менялся. Push, merge и release не выполнялись.
