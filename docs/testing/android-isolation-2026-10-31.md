# Android: изоляция диагностики, 2026-10-31

Контрольная точка D3 поверх `1071871` в `feat/connection-reliability-ux`. Пользователь разрешил установить сборку и проверять подключённый телефон по ADB.

**Результат:** изменено владение рабочими Xray-процессами; создан эксперимент с libbox в отдельном Android-процессе. Продуктовый API проверки пользовательского сервера и его UI ещё не включены. Финальный сетевой прогон не полностью пройден: прямые DNS/HTTPS-запросы требуют дальнейшего разбора. Во всех завершённых экспериментах проверена сохранность VPN либо восстановлена его исходная полная конфигурация.

## Рабочий код

- Xray-сессия и временный latency-тестер владеют отдельными process handles и уникальными конфигурационными файлами.
- Удалены очистка всех процессов по имени `libxray.so` и `pkill`. Закрытие владельца окончательно запрещает последующий запуск, включая запоздалый restart thread.
- Очистка после гибели владельца рассматривает только записанные приватные leases. Проверяются UID, полная команда с точным config token, время запуска дочернего процесса и прекращение исходного владельца.
- Чужая запись, повторно использованный PID, живой или нечитаемый владелец не дают права завершить процесс. Неудавшееся завершение ребёнка не разрешает подмену конфигурации новым запуском.
- Уведомления о смерти ядра и результат отложенного перезапуска привязаны к поколению принятой сессии. Остановка и публикация результата используют один порядок блокировки.

Старые процессы без доказанного владельца не завершаются по догадке.

## Эксперимент, доступный только в debug

В `src/debug` добавлены непубличная bound service `:diagnostics` и Activity в отдельном `:diagnostic_driver`. Activity требует системное разрешение `DUMP`; service не экспортирована. В release этих компонентов нет.

Используется настоящий упакованный `libbox.aar` с синтетической конфигурацией без пользовательских серверов и ключей. Выделены собственные base/working/temp paths, секрет command server и loopback inbound. Клиент управления сверяет уникальный outbound tag именно диагностического ядра.

- Попытка ядра открыть TUN получает отказ.
- Outbound file descriptors привязываются к конкретной физической Android Network; DNS через Android также получает конкретную Network.
- Выбор предпочитает активную физическую сеть. Если активная сеть — VPN, допустим только единственный физический кандидат; неоднозначность завершает проверку ошибкой.
- Потеря выбранной Network не разрешает незаметную смену маршрута.
- Обычное закрытие завершает собственные command client/server. Отмена, deadline и гибель Binder-клиента завершают только диагностический процесс.
- Эксперимент имеет ограничение 20 секунд. Это не публичный API и не фоновый монитор.

Используются публичные [Android Network API](https://developer.android.com/reference/android/net/Network) и [bound service/Binder](https://developer.android.com/develop/background-work/services/bound-services). Фиксированные внешние endpoints вызываются только при явно запущенной проверке.

## Проверки на телефоне

Устройство CPH2747, Android 16, arm64. До обновления сохранены предыдущий APK, localStorage и действительная полная конфигурация. Установка через `adb install -r` сохраняет данные.

### Подтверждённое сосуществование

На первоначальной сборке этапа, SHA-256 `2D94F4A38B4299BE8ABBBF2F99D3F4963423AC728C5FCB023ACE09060C0F61B6`:

- Полный прогон при работающем sing-box: **13 PASS** после усиления контроля живого диагностического PID. Отдельный process/command channel, собственные каталоги, привязка сокетов, DNS, HTTPS 204 и явный SOCKS5 UDP ASSOCIATE с новым outbound binding.
- Обычное приложение с отдельным UID получило HTTPS 204 через VPN при живом диагностическом процессе и после его отмены.
- Отказ создать TUN, гибель Binder-клиента, авария диагностики и новый запуск после аварии сохранили VPN run ID и полный config.
- Отдельная матрица маршрутизации: **8 PASS**, sing-box/Xray, include/exclude, отрицательные проверки кандидатов. Полная конфигурация и настройки восстановлены.

Для Xray с исходной политикой контрольный HTTPS не проходил **до запуска диагностики**. Этот прогон не доказывает проблему изоляции и не засчитан как успешный. При Xray с VPN только для тестового приложения удалось получить стабильный baseline, затем **11 PASS**, включая HTTPS при живой диагностике, отмену и гибель клиента. Следующая попытка диагностического HTTPS не завершилась; полный Xray-прогон остался неполным. Неуспешные baseline-попытки сохранены, а не скрыты повтором.

### Исправления после ревью и окончательная сборка

Ревью `1071871..3d76315` не нашло Critical/Important проблем рабочего кода. Замечание к доказательности проверки повышено до Important: успешный HTTPS мог завершиться после 20-секундного deadline диагностики. Исправлено одним проходом:

- Сверяются тот же PID и нетерминальное состояние до запуска обычного запроса, между опросами и непосредственно перед принятием результата.
- Отсутствующий, сменившийся или нечитаемый процесс запрещает положительный результат.
- До запуска диагностики требуются два последовательных стабильных контрольных запроса. Каждая попытка сохраняется; провал сосуществования автоматически не повторяется.
- Регрессия воспроизвела ложный PASS при смерти диагностики во время запроса; после исправления проходит.

На устройстве также обнаружен произвольный выбор первой физической сети. Контроль показал, что первой была мобильная сеть, тогда как активной — Wi-Fi. Добавлен явный выбор активной сети; регрессии порядка перечисления и неоднозначного fallback сначала упали, затем прошли.

Окончательная установленная сборка, SHA-256 `65E034D054359D4DD5756C7F0B95661C52C4C89165556168B25557DEB2B8DDD3`:

- **9 PASS** действий карточки/отмены профилей, с восстановлением исходной конфигурации.
- Два контрольных HTTPS через исходный VPN прошли.
- Диагностика выбрала активную Wi-Fi Network, создала отдельный процесс и привязала outbound socket; UDP DNS завершился `SocketTimeoutException`. **Полный прогон 13 случаев на этой сборке не пройден.**
- Отдельный helper без libbox также не получил прямой HTTPS через первую мобильную и предпочтительную Wi-Fi сеть, UDP к DNS сети и к фиксированному публичному DNS. HTTPS через VPN прошёл, Android VPN Network не изменилась.
- Этот контроль имеет другой UID и не исключает влияние Android routing/lockdown policy. Он не доказывает поломку сервера или первопричину тайм-аутов. Причину прямых запросов нужно уточнить до включения продуктовых проверок.
- Итоговая сверка: работает sing-box; полный config, profiles, settings, selection и принятое имя соответствуют исходным. Принудительное закрытие обычной задачи по-прежнему останавливает VPN согласно принятому поведению.

## Оставшиеся ограничения

- Minor из ревью отложен: если записанные владелец и ребёнок уже отсутствуют, старый config/lease пока остаётся на диске. Нужна отдельная осторожная очистка, отличающая отсутствие от запрета чтения.
- Полная сетевая проверка на окончательной сборке и полный Xray isolation matrix остаются открытыми.
- Android 7+, always-on/lockdown, смена Wi-Fi/mobile, сон и реальная гибель владельца Xray с orphan recovery требуют отдельной матрицы. Lease policy проверена unit-тестами.
- Синтетический direct proxy не доказывает здоровье конкретного VLESS/Reality/Hysteria2/TUIC профиля.
- Probe generation/snapshot, выбор конкретного сервера, provider config, отмена при Stop/смене сети и продуктовый API остаются следующей частью D3.
- Автовосстановление не включено. Windows/macOS runtime не менялся. Push, merge и release не выполнялись.
